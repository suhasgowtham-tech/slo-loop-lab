# Troubleshooting

Start with `make verify`: it prints which check failed. Then find the symptom below. When asking for help, paste the
**raw output** of the failing command, not a paraphrase.

## Install and platform

| Symptom | Cause and fix |
|---|---|
| `preflight`: *repo is on the Windows drive* | Move it: `cp -r /mnt/c/.../slo-loop-lab ~/ && cd ~/slo-loop-lab`. Bind mounts and file I/O on `/mnt/*` are broken or slow. |
| `preflight`: *docker daemon not reachable* | Start Docker Desktop; Settings → Resources → WSL integration → enable your distro; reopen the WSL terminal. |
| `preflight`: *only N MB visible* | Create `%UserProfile%\.wslconfig` from `docs/wslconfig.example`, then PowerShell: `wsl --shutdown`, reopen WSL. |
| `preflight`: *docker credential helper ... not runnable* | Docker Desktop wrote `"credsStore": "desktop.exe"` into `~/.docker/config.json`; WSL cannot run it and every `docker build` fails. Use the one-line fix printed by preflight (it keeps a `.bak`). |
| `preflight`: *Docker Desktop's built-in Kubernetes is running* | Docker Desktop > Settings > Kubernetes > untick *Enable Kubernetes* > Apply & restart. It is a second cluster that costs RAM and CPU and distorts every latency measurement. |
| `kind create cluster`: *ports are not available* / `/forwards/expose ... 500` | Docker Desktop publishes ports on the Windows side; something there already holds the port. Pick others: `export GATEWAY_PORT=18080 PROM_PORT=19090 GRAFANA_PORT=13000` (put it in `~/.bashrc`), then `make cluster`. |
| `make phaseA`/`phaseB` stops with *Helm release 'slo-loop' is in state 'failed'* | A `helm upgrade --wait` timed out while a run was being prepared (typical causes: the laptop slept mid-run, the llm pod could not start because the model mount went stale, memory pressure). Since v2.4 the matrix repairs once and retries by itself; to do it by hand: `make recover` (= `make heal` + re-apply the release), then `make verify`, then re-run the same `make phaseX` command: finished runs are skipped. `make diag` now also prints the Helm history, recent events and pod logs: paste `results/diag-*.txt` if it happens again. `results/matrix-failures.log` lists every failed attempt. |
| `[matrix] SKIPPED s5_retriever_latency ...` *gateway gives up on the retriever after 10 s* | The s5 delay is 1.5 x the calibrated short threshold (15.6 s at 10.4 s). With the old 10 s retriever timeout every request FAILED instead of being slow (an outage, not a slowdown). The chart now sets `gateway.retrieveTimeoutS: 30`: `make deploy`, `make verify`; runs recorded with the old setting are invalid for H4 and must be moved away (`results/superseded/`) and re-run. |
| `kind load docker-image` fails: *content digest ... not found* | Docker Desktop's containerd image store adds attestations. `scripts/05-build-images.sh` already passes `--provenance=false --sbom=false`; if you build by hand, pass them too. |
| llm pod `CrashLoopBackOff`; its log says *failed to open GGUF file '/models/...gguf' (No such file or directory)*; `make deploy` fails after 8 minutes | After a Windows / WSL / Docker Desktop restart Docker can re-create the kind node's `/models` bind mount **empty** (the Ubuntu distro was not up yet). The file is still safe in `./models`. Run `make heal` (restarts the node container so the mount is re-created, then restarts the pods), then `make deploy && make verify`. `make deploy`, `make verify` and `make preflight` now detect this in seconds. If `make heal` says it is still empty: `make down && make up` (the model download and your results are kept). |
| `preflight`: *other containers are running* / load average high at idle | Other kind clusters or Docker Desktop's Kubernetes share your CPUs and distort every latency number. `docker stop <names>` (reversible with `docker start`), and untick Docker Desktop > Settings > Kubernetes. Idle load average should be well under 1 before `make latency`. |
| `make latency` / `capacity` / `calibrate` print `[quiet] ... waiting` or `[quiet] WARNING: still N` | They wait up to 5 minutes (`LAB_QUIET_WAIT_S`) for the 1-minute load average to fall below max(1.0, 15 % of your CPUs), then measure anyway with a warning. Capacity, idle latency and the SLO thresholds must be measured as quietly as the experiments will run, so fix the cause: `docker ps` / `docker stats --no-stream` (stop other clusters), untick Docker Desktop's Kubernetes, close Windows apps, charger in, power mode *Best performance*. |
| `make calibrate` prints thresholds that look huge (e.g. 15-20 s) or not ordered short < medium < long | At 50 % utilisation with a heavy-tailed request mix, a request mostly waits behind others, so baseline TTFT p99 measures queueing, and the p99 of ~100 samples is nearly their maximum. It is a finding, not a bug, and it makes the SLO loose. Check `results/calibration/baseline-*.csv` (the raw data) and `make diag` (is the machine quiet? is the llm pod CPU-throttled?). A quieter machine and more samples (`slo-lab calibrate --duration 2400`) tighten it. |
| `make capacity` reports capacity far below the idle estimate (e.g. 55 %) | Two requests in flight share the same 2 threads, and any CPU used by other programs counts against the llm pod. `make diag` shows `nr_throttled` (CPU limit biting) and the busiest containers; stop what you do not need. The probe's resolution is one x1.25 step with ~20 requests per step, so treat capacity as +-25 %. |
| `preflight`: *port in use* | Another process holds 8080/9090/3000. Stop it or run e.g. `GATEWAY_PORT=18080 make cluster`. The same variable must be exported for later commands (`export GATEWAY_PORT=18080`). Changing a port needs a new cluster (`make down && make cluster`). |
| `make venv` fails | `sudo apt-get install -y python3-venv python3-pip` |
| `make tools`: *GitHub API rate limit* | Wait a few minutes and retry, or install kind/kubectl/helm yourself (Helm must be 3.x). |
| `kind create cluster` hangs or fails | Check Docker Desktop has ≥ 8 GB available to WSL; `kind delete cluster --name slo-loop` then `make cluster`. |
| *models mount missing inside the node* | The repo is not on the Linux filesystem, or the cluster was created before `./models` existed: `make down && make cluster`. |
| `make platform`: a chart install times out | `kubectl --context kind-slo-loop -n <ns> get pods` shows the stuck pod. On a slow link the first image pulls can exceed 10 min: simply re-run `make platform` (it is idempotent). |
| node-exporter / etcd / scheduler targets down in Prometheus | Intentionally disabled for kind (see `platform/values/kube-prometheus-stack.yaml`); not an error. |

## Model and llama.cpp

| Symptom | Cause and fix |
|---|---|
| `make model`: checksum mismatch | Delete `models/*.gguf` and retry. If it persists, Hugging Face changed the file: set `LAB_MODEL_REPO`/`LAB_MODEL_FILE` (and the chart value `llm.modelFile`). |
| llm pod `CrashLoopBackOff`, log mentions unknown argument | The `:server` image changed its flags. Run `kubectl --context kind-slo-loop -n slo-loop logs deploy/llm`; remove or rename the flag in `charts/slo-loop-app/templates/llm.yaml`. `make pin-images` freezes a known-good image afterwards. |
| llm pod stuck `Pending` | Not enough CPU for the requested replicas: `kubectl describe pod`. Lower `autoscaling.maxReplicas` or the llm CPU requests in `charts/slo-loop-app/values.yaml`, or give WSL more processors. |
| llm pod `OOMKilled` | Raise `llm.resources.limits.memory` or lower `llm.ctxSize`. |
| `verify`: *stream ends with a stop=true chunk* fails | The streaming format of your llama.cpp build differs from the gateway's assumption. `verify` prints the RAW lines; adapt the parsing in `apps/gateway/app.py` (the `stop` check) and `tests/fake_llama.py`, then `make images deploy`. Until fixed every request is `llm_incomplete`. |
| `verify`: `/metrics` warning | `--metrics` unsupported by that build. The lab does not use llama.cpp metrics; set `llm.metrics=false` in the chart values. |
| requests fail with a context-size error | A prompt exceeded the per-slot context (`ctxSize / parallel`). Raise `llm.ctxSize` (a 0.5B model's KV cache is ~12 KB/token, so this is cheap). |

## Observability

| Symptom | Cause and fix |
|---|---|
| gateway/retriever targets not up in Prometheus | `kubectl -n slo-loop get servicemonitors`; Prometheus must select them (`serviceMonitorSelectorNilUsesHelmValues: false` is set). Check `kubectl -n slo-loop get endpoints`. |
| `slo:burn_rate:*` series missing | The rule group evaluates every 5 s; wait 30 s after the first request. Check Prometheus → Status → Rules for errors. |
| Grafana has no *SLO-Loop Lab* dashboard | The sidecar watches ConfigMaps labelled `grafana_dashboard=1` in all namespaces: `kubectl -n slo-loop get cm slo-loop-dashboard`; restart Grafana (`kubectl -n monitoring rollout restart deploy/kps-grafana`). Login admin / `slo-loop-lab`. |
| `kubectl top` fails (CPU policy useless) | metrics-server not ready: `kubectl -n kube-system logs deploy/metrics-server`. Values enable `--kubelet-insecure-tls`, required on kind. |

## Autoscaling

| Symptom | Cause and fix |
|---|---|
| KEDA policy never scales | `kubectl -n slo-loop describe scaledobject llm` and `kubectl -n slo-loop get hpa`. For `queue`/`burn`, the query must return a value from Prometheus: run it in the Prometheus UI. The address must be `http://kps-prometheus.monitoring.svc:9090`. |
| Replicas flap | Raise `autoscaling.scaleDownStabilizationSeconds`. Flapping is a *result* in an autoscaling study; record it, do not hide it. |
| A run is marked invalid: *replicas at t0* | A previous scale-down was still in progress. The runner restarts workloads before each run; if it persists, check for pods stuck `Terminating`. |

## Experiments

| Symptom | Cause and fix |
|---|---|
| Run invalid: *load generator lag* | The client could not keep to the schedule (CPU starved). Close other applications, plug in power, reduce `base_rps` (re-run `make capacity`), or give WSL more processors. Never publish runs with this flag. |
| Run invalid: *requests dropped client-side* | `max_outstanding` was reached: the system was so overloaded that the client capped concurrency. Lower the offered load or raise the cap in `config/load.yaml`. |
| `s6_netem_delay` skipped | Your WSL2 kernel has no netem. This is detected by `make chaos-preflight` and the scenario is skipped rather than faked. A custom WSL kernel with `CONFIG_NET_SCH_NETEM` enables it. |
| StressChaos / PodChaos do not inject | `kubectl -n chaos-mesh get pods`; the namespace must carry `chaos-mesh.org/inject=enabled` (set by `make cluster`) and the runtime must be containerd (set in `platform/values/chaos-mesh.yaml`). |
| `make capacity`: *even the first step degraded* / *degraded even at X rps after 3 retreats* | The probe already halves its start rate three times, so this means the machine is not delivering the CPU the cluster expects. In order: (1) Windows power mode **Best performance** and the charger plugged in; (2) turn off Docker Desktop's own Kubernetes (Settings > Kubernetes); (3) close browsers/IDEs; (4) `uptime` should show a load average well under 1 when idle; (5) `make latency` should report a mean service time under ~6 s, otherwise `make profile P=lite`. |
| `make latency` reports a mean service time above ~12 s | The workload is too heavy for this CPU: a 10-minute run would contain too few requests for a 99 % SLO. `make profile P=lite`, then `make latency` again. |
| `make capacity` says *not verified* / `Run: make verify` | `make deploy`, `make cluster` and `make down` invalidate the last verification on purpose. Run `make verify`; when it is green the gate opens. |
| `make capacity` says *Helm release 'slo-loop' is not deployed* | `make up` did not finish. `make images && make deploy && make verify` resumes it. |
| Detector table shows `x 3` or `x 6` | Not an error: at laptop request rates a 5 s window holds ~1 event, so each detector's windows are stretched equally until its shortest window holds enough events (docs/DESIGN.md, *low-traffic alerting*). `rules` shows how many of its rules fit in the run. |
| Results look implausible | Open `results/runs/<phase>/<run>/requests.csv`: check `status` counts. Run `.venv/bin/slo-lab summarize <run-dir>` for latency per class and every detector's verdict. |
| Interrupted run left a fault active | `kubectl --context kind-slo-loop delete -f chaos/ --ignore-not-found` and `curl -X DELETE http://127.0.0.1:8080/admin/retriever-fault` (the CLI also does this on Ctrl-C). |

## Long runs: tmux, power, Docker restarts, and the health gate

| Symptom | Cause and fix |
|---|---|
| The laptop restarted (Windows Update, power loss, crash) and you do not know what is finished | Open Docker Desktop and wait for *Engine running*, open Ubuntu, then run **`make status`**. It is read-only and prints, on one screen: whether Docker, the kind node and the three deployments are up, whether the host logger runs, how many runs of each phase are finished, which run folders were started but never finished (they are redone automatically), the last gate, and the ONE next command (for example `make heal && make verify`, or the hands-off chain `make gate && { make phaseB REPS=3; make gate; make health PHASE=B; }`). To see WHY Windows restarted, open **Windows PowerShell (not Ubuntu)** and run: `Get-WinEvent -FilterHashtable @{LogName='System'; Id=41,1074,6008; StartTime=(Get-Date).AddDays(-5)} \| Select-Object -First 8 TimeCreated, Id, Message \| Format-List`  (1074 = a planned restart, usually Windows Update; 6008 and 41 = unexpected shutdown, power loss or crash). |
| Windows says the shutdown was **unexpected** (Event 41 "rebooted without cleanly shutting down" and Event 6008, real case: Saturday 14 Nov 08:33, the laptop was idle) | That is not Windows Update (an update restart is Event 1074). The laptop lost power or froze and was switched off. For an idle laptop the usual cause is an empty battery: keep the charger plugged in whenever the lab is up (also between experiments), and in Settings > System > Power & battery set *Screen and sleep* to **Never** for both *On battery* and *Plugged in* while the lab runs. Finished runs are never lost (a run is only finished when its DONE file exists); after the next start run `make status` and follow its NEXT line. If it happens while the charger IS plugged in, suspect heat or hardware: run the laptop's own diagnostics (Dell SupportAssist) and keep the vents free. |
| `make rerun-bad` finished but `make status` still shows flagged runs (real case, 17 Nov: 16 flagged, all re-run on a healthy machine, 7 flagged AGAIN, always the same runs: `s2_long_shift ... r2` for 4 policies, `s7_slow_burn__static1__r2`, `s6_netem_delay__static1__r4`) | Same scenario + same rep means the SAME traffic (the seed depends only on those two). A run that is flagged again after a re-run on a machine that just passed a gate is reproducible: a property of that traffic draw (for example a burst of simultaneous arrivals queueing on one replica), not host noise. Re-running it again gives the same result and costs 11 minutes per run. Keep it: `make gate && make accept-flagged PHASE=B` (and `PHASE=A`). It records the decision in results/accepted-flags.csv, shows the run as `accepted:SLOW` in `make health`, and the run stays in the analysis (report it as flagged-but-reproducible, and run the analysis with and without it). INVALID runs are never accepted: they must be re-run. |
| `make accept-flagged PHASE=A` says `kept N` but `make status` counts more accepted runs than you accepted | Fixed in v2.6.0. Up to v2.5.9 the accepted-flags file matched runs by NAME only, and the same name exists in Phase A and Phase B (`s2_long_shift__static1__r2`), so keeping the Phase B run silently kept the Phase A run too. Since v2.6.0 the key is (phase, name): the Phase A run shows as flagged again until you run `make gate && make accept-flagged PHASE=A` for it. |
| A run you left unattended is gone when you come back | tmux protects a run from a closed terminal window, **not** from the laptop sleeping, losing power or WSL being shut down (that ends every process in WSL, tmux included). So: (1) start long runs inside tmux: `tmux new -s lab`, run the command, detach with **Ctrl+b then d**, come back with `tmux attach -t lab` (`tmux ls` lists sessions); (2) plug in the charger; Windows Settings > System > Power: *Power mode* **Best performance**, *Screen and sleep* **Never** when plugged in, and *lid close* **Do nothing** (Control Panel > Power Options > Choose what closing the lid does). Your results are safe on disk; `make heal`, `make verify`, then run the same command again: finished runs are skipped. |
| `make gate` says **GATE FAIL** | The machine is slower than the one that was calibrated (real case: 100 % good at night, 89 % a few hours later, median TTFT 3x higher). Do not start a long run. Plug in, Best performance, close Chrome and other apps, run `make diag` and stop every container it lists besides `slo-loop-control-plane`, wait 10 minutes untouched, `make gate` again. `.venv/bin/slo-lab gate --history` shows every earlier gate. |
| Other kind clusters (`kind-control-plane`, `lab-control-plane`, ...) are running | Docker restarts old containers after every Docker/Windows restart and each kind cluster burns about half a core idle. `docker stop NAME ...` (nothing is deleted) and `docker update --restart=no NAME ...` so they stay off. `make gate` and `make diag` print the exact commands with your container names. |
| Docker Desktop: **WSL is unresponsive** (`CommandTimedOut`) | Docker's watchdog asked Windows for `wsl.exe --version` and got no answer in time: the machine was overloaded (all CPUs busy, little RAM left for Windows). Not necessarily a crash. Check the run is alive (newest `DONE` file under results/runs is < 13 min old) before clicking anything; **Restart** kills the run in progress. If it is really hung: Quit Docker Desktop, PowerShell `wsl --shutdown`, start Docker Desktop, wait for *Engine running*, then `make heal && make verify`. |
| `docker` says *could not be found in this WSL 2 distro*, and `make heal` used to say *the cluster is gone* | Docker Desktop is stopped, still starting, or its WSL integration is off (Settings > Resources > WSL integration > Ubuntu). The cluster is **not** lost. Start Docker Desktop, wait for *Engine running*, `docker ps -a` (the node `slo-loop-control-plane` is listed), `make heal && make verify`. Only if `docker ps -a` works and does not list the node: `make up`. |
| The laptop restarted by itself in the middle of a run (**Windows Update**) | Windows installs updates and restarts at night or while you are away; that ends WSL, Docker and the run. Before a long run: Settings > Windows Update > install everything that is pending, **restart now**, then *Pause updates* (1 week, repeat as needed) and set *Active hours* to cover the whole run. After a restart: start Docker Desktop, wait for *Engine running*, `make heal && make verify && make gate`, then run the same matrix command again (finished runs are skipped; the run that was in progress starts over). |
| `deployment/llm did not reach 1 ready replicas ... (spec/ready=(2, 2))` right after a **cpu** run | Fixed in v2.5.3+: switching from a KEDA policy to `static1` could leave 2 replicas because the autoscaler's HPA disappears a few seconds after Helm removes it and scaled the Deployment back up once. The harness now waits for the autoscaler to be gone and sets 1 replica itself (also in `make recover`). On an older version: `kubectl --context kind-slo-loop -n slo-loop scale deploy/llm --replicas=1`, then run the same matrix command again. |
| The gate passed before a long run but **FAILS after it** (real case: 100 % good at the start, 90.7 % and median TTFT 3.3 s vs 0.76 s at the end) | Something made the laptop slower DURING the run. Find out which runs were affected: `make health PHASE=B` prints, per run, the good % and the short-prompt median TTFT of its steady stretch (the first minutes, before the load or the fault changes; same traffic for every policy) and flags **BAD**, **SLOW** or **INVALID**. Re-run flagged runs with `.venv/bin/slo-lab run --phase B --scenario NAME --policy NAME --rep 1 --force`. To learn the CAUSE, start the host logger in a second tmux window before the long run: Ctrl+b then c, then `make hostlog` (Ctrl+b then 0 goes back). `make health` then adds host CPU busy %, **steal %** (Windows taking CPU away from WSL: Windows Update, Defender, power or heat limits) and lowest free memory per run. Busy while nothing measures = something inside Docker (the `top_container` column of results/hostlog.csv names it). |
| A `burn`-policy run says `valid=False (replicas at t0 were 3, expected 1)` | The burn trigger reads a 120 s window and Prometheus keeps answering with the series of the gateway pod that was just replaced, so the tail of the previous run (a ramp ends in overload) scaled the llm out before this run started. Fixed in v2.5.4: before switching the burn policy on, the harness waits until the 120 s burn rate is back near 0 (at most 4 minutes). On an older version: re-run that run with `--force`. |
| `make health` flags runs (**BAD**, **SLOW** or **INVALID**) | Those runs were measured on a slow host or started in a wrong state. Re-run exactly those, **hands-off**: `make gate && make rerun-bad PHASE=B` (also `PHASE=A` or `PHASE=X`). It refuses to start unless a gate passed in the last 90 minutes, re-runs each flagged run with `--force`, and takes about 12 minutes per run. Afterwards run `make gate` and `make health PHASE=B` again: every row should show `-` in the flags column. The rule for ALL runs and gates: plug in the charger, close Chrome, ChatGPT, WhatsApp, Teams and OneDrive, and do not touch the laptop while anything is measuring (real case: the same laptop failed three gates in a row while it was in use, then passed two gates and four re-runs in a row while it was left alone). |

## Start over

`make down` removes the cluster but keeps `models/` and `results/`. `make clean` removes the virtualenv and caches.
